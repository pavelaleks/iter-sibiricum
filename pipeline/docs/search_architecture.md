# Поиск по корпусу Iter Sibiricum: архитектура

Проект, 28.11.2026. Статус: предложение. Реализация ещё не начата.

## Задача

Сейчас искать можно по автору и названию книги (в библиотеке) и по тексту одной книги (в режиме чтения). Поиска по всему корпусу нет: 109 книг, 165 365 абзацев, около 11,4 млн словоупотреблений на девяти языках (en 68 книг, fr 17, de 14, fi 3, da 2, it 2, pl, cs, no — по одной).

Предлагаются два уровня поиска с разным статусом:

1. **Точный (лексический) поиск.** Он находит слово, форму, фразу или сочетание слов на заданном расстоянии. Его результаты воспроизводимы и пригодны для подсчётов и цитирования.
2. **Смысловой (семантический) поиск.** Он находит фрагменты, близкие запросу по смыслу, на любом языке корпуса, например по русскому запросу «отношение к шаманам». Это эвристический инструмент для поиска материала. Количественные выводы на нём не строятся, и на странице поиска это сказано прямо.

Оба уровня работают без сервера, на GitHub Pages, как и весь сайт.

## 1. Точный поиск

### Хранение: SQLite FTS5, читаемая из браузера по частям

Индекс собирается в базу SQLite с полнотекстовым модулем FTS5. В браузере её читает SQLite, скомпилированный в WebAssembly, — библиотека sql.js-httpvfs или аналог. Браузер загружает не всю базу, а только нужные запросу страницы, через HTTP-запросы с диапазоном байтов (Range). Этот способ хорошо отработан на GitHub Pages.

Прототип собран на полном корпусе (`unicode61 remove_diacritics 2`, префиксный индекс от 3 букв, страница 32 КБ):

| часть базы | объём |
|---|---|
| полнотекстовый индекс (с позициями слов) | 59 МБ |
| тексты абзацев для показа контекста | 71 МБ |
| метаданные абзацев (книга, язык, год, период, страна, регион) | 11 МБ |
| всего | 142 МБ |

Скорость запросов в прототипе (локально, без сети): `shaman*` — 301 абзац за 2 мс; `Ostiak NEAR(fish, 10)` — 15 абзацев; `tungus* OR toungous* OR tungusen` — 725 абзацев. По сети запрос обычно стоит нескольких запросов Range общим объёмом в сотни килобайт.

Технические условия:
- GitHub Pages не принимает файлы больше 100 МБ, поэтому база делится на части по 10 МБ (режим chunked в sql.js-httpvfs).
- CDN GitHub Pages игнорирует заголовок Range, если ответ сжимается gzip. Поэтому запросы к базе нужно отправлять с заголовком `Accept-Encoding: identity`; при сборке это проверяется командой curl.
- Тексты абзацев можно вынести в отдельную базу. Тогда сам поиск будет легче, а контекст будет подгружаться только для показанных результатов.

### Нормализация и расширение запроса

Это главное научное достоинство поиска: запрос расширяется по словарям проекта.
- **Этнонимы.** Запрос «якуты» или `Yakut` разворачивается во все формы из словаря этнонимов (`pipeline/data/ethnonyms.csv`) на десяти языках: Yakuts, Iakoutes, Jakuten и т. д. Пользователь видит, какие формы вошли в запрос, и может отключить любую из них.
- **Топонимы.** Запрос «Иркутск» разворачивается во все написания, засвидетельствованные в книгах (`place_mentions.csv`, газеттир LPF): Irkoutsk, Irkuck и т. д.
- **Орфография.** Учитываются регистр и диакритика (Tungüsen = Tungusen). Морфология учитывается только по явному запросу (`shaman*`). Автоматический стемминг не применяется: для исторических текстов с ошибками распознавания он даёт больше ложных совпадений, чем пользы.

### Интерфейс и результаты

- Отдельная страница `#search`. С главной страницы запрос передаётся туда.
- Синтаксис запроса: слова, «фраза в кавычках», `слово*`, `NEAR(a b, 10)`, OR и NOT.
- Фильтры: язык, период, страна автора, книга, «только абзацы о Сибири». Под каждым фильтром показано число найденных абзацев.
- Результаты выводятся строками конкорданса (KWIC): найденное слово в контексте, книга, год, ссылка на абзац в режиме чтения (`#book-…-p00123`).
- Распределение найденного по десятилетиям поездок дано как в абсолютных числах, так и в нормированном виде (на миллион слов).
- Выгрузка в CSV, постоянная ссылка на запрос и библиографическая ссылка на абзац — как на странице «Свидетельства».

### Сборка

Скрипт `pipeline/analysis/12_search_index.py` запускается в `run_all.sh` после `10_build_site.py`. Скрипт проверяет число абзацев в базе и в `texts/`, выполняет контрольные запросы и сверяет их с ожидаемым числом совпадений.

## 2. Смысловой поиск

### Векторные представления абзацев

- Модель — многоязычная, с открытой лицензией: `intfloat/multilingual-e5-small` (384 измерения). Она работает и в Python при сборке, и в браузере (Transformers.js, ONNX). Более сильная `BAAI/bge-m3` (1024 измерения) пригодна для сборки, но слишком тяжела для браузера.
- Индексируются абзацы длиннее 20 слов; длинные абзацы делятся на окна примерно по 200 слов. Служебные части книг (оглавления, указатели) исключаются: они уже размечены при сегментации.
- Хранение строится по принципу «разбиение на кластеры + сжатие»:
  - векторы кластеризуются (k-means, около 512 кластеров) и квантуются до int8;
  - каждый кластер записывается отдельным файлом, около 100–150 КБ;
  - по запросу браузер вычисляет вектор запроса, выбирает 8–16 ближайших кластеров и загружает только их (1–2 МБ), затем сравнивает векторы точно.
  - Весь индекс — порядка 60 МБ в файлах, но за один запрос загружается малая его часть.

### Вычисление вектора запроса

Есть два варианта:
- **В браузере.** Модель multilingual-e5-small в ONNX int8 весит 118 МБ. Она загружается один раз, по явному согласию пользователя («включить смысловой поиск»), и хранится в кэше браузера. Объём можно сократить в несколько раз, если обрезать словарь модели до токенов языков корпуса и русского. Это нужно проверить отдельно.
- **Через небольшой внешний сервис.** Это облачная функция, которая только вычисляет вектор запроса. Вариант быстрее для пользователя, но делает сайт зависимым от внешней службы. При её недоступности остаётся точный поиск.

Рекомендуется начать с браузерного варианта: у него нет внешних зависимостей, и его проще описать в методике.

### Совмещение с точным поиском

Режим «оба» объединяет два списка методом взаимного ранга (Reciprocal Rank Fusion). У каждого результата указано, каким способом он найден.

### Проверка качества

Сравнение строится так же, как остальные проверки на сайте:
1. Коллектив формулирует 40–60 запросов по исследовательским вопросам проекта: на русском и на языках источников.
2. Для каждого запроса объединяются первые 20 результатов трёх режимов. Эксперт оценивает релевантность каждого фрагмента без знания режима, который его нашёл.
3. Для каждого режима считаются nDCG@10 и полнота среди первых 20 результатов (recall@20); итог публикуется в таблице проверок на странице «Метод».

Смысловой поиск включается для читателей, только если он заметно превосходит точный поиск с расширением по словарям — особенно на межъязыковых запросах.

## Этапы

| этап | содержание | оценка |
|---|---|---|
| 1 | база FTS5, расширение по словарям, страница `#search` с фильтрами, KWIC, CSV | 3–4 рабочих дня |
| 2 | векторный индекс, браузерная модель, режим «оба» | 3–5 дней |
| 3 | проверочные запросы, экспертная оценка, решение о включении смыслового поиска | 1–2 дня работы коллектива |
